# decomposition-contract: lessons

Distilled lessons for the architect role, each as rule, cause and
application: where a child's contract comes from, how a plan enters review,
how repository and third-party facts are verified, and how a rework verdict
is decomposed.

**Children inherit the issue mirror's acceptance criteria, including where the deliverable goes.** Why: a chain of children published a triage table as an issue comment while the mirror required a document in the repository plus a back-reference from code; the gap surfaced only when the root was closed. Apply: copy the mirror's criteria verbatim into the publishing child; before closing the root, compare the deliverable's venue with the mirror; turn unmet criteria into a follow-up card with an idempotency key; do not close the mirror or tick its boxes for the worker.

**The plan goes into the built-in review lane.** Why: separate "review the plan", "rework the decomposition" and "re-review" cards duplicated the built-in loop and stalled the work; a child created open went to work before the plan verdict, because the dispatcher spawns ready cards every few minutes. Apply: (1) create the children held back from dispatch and linked to the root: create, `kanban link <root> <child>`, then `block --kind dependency` (the canonical form in kanban-discipline; a card created with `--initial-status blocked` is released only by hand); (2) publish the plan document as a comment on the root and the issue mirror; (3) call `kanban_request_review` on the ROOT with a summary: what the plan is, how many children, where the document is, what to look at first. The reviewer's `kanban_complete` means the plan is accepted and releases the children; `kanban_request_changes` returns the root to you with the round history. More than three children, or API, migrations or security touched: always send the root to review; in doubt, send it.

**Repository facts are checked in code, not from memory.** Why: long, expensive review loops were sustained by findings like an unrunnable integration runner, wrong CI job names, a wrong endpoint path and wrong relevant files, all checkable in minutes. Apply: open every path in Relevant Files (`find_symbol` or `read_file`) and cite `file:line`; confirm the test runner and required-check job names in the build files and CI workflows; confirm an endpoint by its handler; check the dependency graph for deadlocks (no child depends on its parent, the root depends on all children); list in the summary what was confirmed by what.

**A third-party API is checked by its source, ours by the code.** Why: a compatibility matrix for twenty-odd tools was built on a class that did not exist in the pinned library version. Apply: context7 for docs of the exact version from the manifest; serena for symbols in our code; the dependency's own artifacts when docs are silent (for example `javap -cp <jar> <class>` proves a method exists); web search for release notes and upstream issues. Every claim carries its source: `file:line` for ours, a link or class name with version for theirs.

**A rework verdict decomposes into a chain on the verdict PR's branch.** Why: parallel blocks of one verdict each opened their own stacked PR and the owner got three or four PRs to review and merge instead of one. Apply: each child's body names the push target ("branch of PR #N: <branch>"), no new PR; children are chained with `kanban link` in order, never parallel on one branch. Full mechanics: kanban-discipline, "Rework for a verdict lives in the verdict PR's branch".
